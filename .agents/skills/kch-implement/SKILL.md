# KCH 기능 구현

1. 관련 이슈 본문·댓글·선행 작업과 현재 변경 상태를 확인하고 업무 용어·관련 ADR을 읽는다.
2. 구현할 사용자 행동과 완료 기준을 짧게 정리한다. 이미 합의한 요구사항과 테스트 경계는 재승인받지 않고 중요한 미결정 사항만 확인한다.
3. 화면·API·DB·테스트를 연결하는 작은 단위로 진행한다. UI만 만든 것을 기능 완료로 보고하지 않는다.

## TDD

- 업무 기능·버그는 사용자 행동을 표현한 테스트 한 개를 먼저 작성하고 실제 실패 이유를 확인한다. 최소 구현으로 통과시킨 뒤 다음 동작으로 진행한다.
- 주 테스트 경계는 실제 HTTP API와 실제 SQLite다. 내부 함수·SQL 호출 순서 대신 응답과 다음 조회 결과를 검증한다.
- 권한·중복 상태 변경·DB 제약·롤백을 우선 검증하고 운영과 같은 드라이버·제약을 사용한다.
- 프론트는 입력·저장·오류 안내를 검사하고 브라우저에서 핵심 흐름을 확인한다. 외부 인증의 통제된 테스트와 운영 검증을 구분한다.
- 이미 작성된 구현은 테스트가 나중에 추가됐음을 숨기지 않는다. 새 동작과 발견한 결함부터 실패→통과 순서로 진행한다.
- 문서·문구·순수 스타일 변경에는 불필요한 테스트를 만들지 않고 문서·화면을 검증한다.

## 마무리

- 변경한 테스트 파일과 타입 검사를 작업 중 실행한다. 관련 전체 테스트·정적 검사·빌드는 마무리할 때 실행하고 새 변경·실패 없이 반복하지 않는다.
- 화면 변경은 가상 정보로 직접 확인한다. 저장 기능은 재시작 후 조회도 확인한다.
- 변경 코드 리뷰는 공통 `kch-review` 스킬을 읽고 수행한다. 사용하지 않은 도구나 독립 리뷰를 받았다고 보고하지 않는다.
- 이슈와 보고에서 완료·미완료, 로컬 검증·GitHub CI·main 반영·배포를 구분한다.
- 커밋·PR이 요청된 경우 해당 공통 스킬을 읽는다. 이 스킬 자체가 push·PR·병합을 추가로 허가하지 않는다.
