## Problem Statement

직원은 어떤 사내 장비를 빌릴 수 있는지, 본인의 신청과 반납이 처리되었는지 쉽게 확인해야 한다. 관리자 한 명은 같은 모델의 여러 장비를 자산번호로 구분하고, 중복 대여 없이 신청 승인·반납 확인·전체 대여 현황을 관리해야 한다. 비개발자도 변경 내용을 이해하고 자동 검사를 거친 배포를 운영할 수 있어야 하며, 소규모 사용량에 맞춰 클라우드 비용을 줄여야 한다.

## Solution

Google 로그인과 사전 등록 이메일 허용 목록으로 사내 직원만 접근하는 웹서비스를 만든다. 직원은 개별 자산을 선택하여 반납 예정일과 함께 대여를 신청하고, 관리자 승인 즉시 대여가 시작된다. 반납은 직원 요청 후 관리자가 확인해야 완료된다. 관리자는 자산·허용 직원·전체 대여 현황을 관리하며, 업무 이력은 실제 DB에 영구 저장한다.

프론트엔드는 기존 유료 Vercel 계정에, Go 백엔드와 SQLite 영구 볼륨은 Railway에 배포한다. 공개 GitHub 저장소에서 PR의 빌드·테스트를 필수로 하고 main 병합 시 DB 마이그레이션과 운영 배포를 자동 실행한다. 재배포 시 짧은 중단은 허용한다.

개발 진행 순서 변경(2026-10-21): 로컬 개발은 직원·관리자 테스트 계정으로 진행한다. #2는 로컬 셋업·개발 로그인 범위로 조정하고 실제 Google 로그인 구현·운영 연결·최종 검증은 #10으로 옮긴다. 운영 인증 정책은 Google 로그인과 사전 등록 이메일 허용 목록을 유지한다.

추가 범위 변경(2026-10-21): 직원 이메일 등록·비활성화 관리 화면(#3)은 제외한다. 테스트 직원 1명과 테스트 관리자 1명으로 개발하고 #4를 진행한다. 아래 직원 관리 UI 관련 사용자 이야기는 현재 범위에서 제외되며 운영 허용 이메일·관리자 지정은 #10의 설정과 검증으로 처리한다.

## User Stories

1. 직원으로서 Google 계정으로 로그인하여 별도 비밀번호 없이 서비스를 사용하고 싶다.
2. 관리자로서 허용할 직원 이메일을 미리 등록하여 사내 사람만 접근하게 하고 싶다.
3. 미등록 사용자로서 접근이 허용되지 않았다는 안내를 받아 로그인 실패 이유를 알고 싶다.
4. 직원으로서 로그아웃하여 공유 기기에서 내 계정의 접근을 종료하고 싶다.
5. 관리자로서 직원 계정을 비활성화하여 기존 로그인 상태에서도 접근을 중단시키고 싶다.
6. 직원으로서 전체 장비 목록을 조회하여 이용 가능한 장비를 찾고 싶다.
7. 직원으로서 자산번호·장비명·모델·분류·설명·보관 위치·상태를 확인하여 필요한 개별 장비를 선택하고 싶다.
8. 직원으로서 대여 가능·대여 중·수리 중인 장비를 구분하여 신청 가능 여부를 알고 싶다.
9. 직원으로서 개별 자산을 선택해 대여를 신청하여 필요한 장비를 사용하고 싶다.
10. 직원으로서 반납 예정일을 필수로 지정하여 언제까지 사용하는지 알리고 싶다.
11. 직원으로서 다른 직원의 신청이 대기 중인 장비에도 신청하여 관리자 판단을 기다리고 싶다.
12. 직원으로서 본인의 대기 신청을 취소하여 더 이상 필요하지 않은 요청을 철회하고 싶다.
13. 직원으로서 본인 신청의 대기·승인·거절·취소 결과를 확인하여 처리 상태를 알고 싶다.
14. 직원으로서 거절 사유를 확인하여 신청이 받아들여지지 않은 이유를 이해하고 싶다.
15. 직원으로서 승인되면 바로 대여 중으로 표시되어 별도 인도 확정 없이 사용 현황을 확인하고 싶다.
16. 직원으로서 본인이 대여 중인 장비와 반납 예정일을 조회하여 반환을 준비하고 싶다.
17. 직원으로서 반납 예정일을 넘긴 대여의 연체 표시를 확인하여 반환할 장비를 알고 싶다.
18. 직원으로서 연체 중에도 반납 요청을 보내 대여를 정상 종료하고 싶다.
19. 직원으로서 대여 중인 자산의 반납을 요청하여 관리자 확인을 받고 싶다.
20. 직원으로서 반납 요청이 확인 대기 중임을 알아 실제 반납 완료와 구분하고 싶다.
21. 직원으로서 반납 요청 거절 사유를 확인하여 문제를 해결하고 다시 요청하고 싶다.
22. 직원으로서 반납 완료와 과거 대여 이력을 조회하여 내 사용 기록을 확인하고 싶다.
23. 직원으로서 다른 직원의 대여 이력이 노출되지 않아 내 업무 정보도 보호받고 싶다.
24. 관리자로서 고유한 자산번호로 장비를 등록하여 같은 모델도 개별 관리하고 싶다.
25. 관리자로서 자산 정보를 수정하여 장비 정보와 보관 위치를 최신으로 유지하고 싶다.
26. 관리자로서 자산을 수리 중으로 전환하여 새 대여 신청을 막고 싶다.
27. 관리자로서 수리 중으로 전환한 자산의 대기 신청이 자동 거절되어 처리 누락을 막고 싶다.
28. 관리자로서 수리가 끝난 자산을 다시 이용 가능하게 하여 대여를 재개하고 싶다.
29. 관리자로서 더 이상 사용하지 않는 자산을 삭제 처리하여 새 신청 목록에서 제외하고 싶다.
30. 관리자로서 삭제한 자산의 과거 대여 이력을 유지하여 사용 기록을 확인하고 싶다.
31. 관리자로서 진행 중인 대여가 있는 자산의 삭제를 차단하여 반납 대상을 잃지 않고 싶다.
32. 관리자로서 대기 중인 전체 신청을 확인하여 승인과 거절을 처리하고 싶다.
33. 관리자로서 개별 신청 한 건을 승인하여 해당 자산의 대여를 시작하고 싶다.
34. 관리자로서 한 신청 승인 시 같은 자산의 나머지 대기 신청이 자동 거절되어 중복 대여를 막고 싶다.
35. 관리자로서 사유와 함께 신청을 거절하여 직원에게 결과를 설명하고 싶다.
36. 관리자로서 반납 요청 목록을 확인하여 실제로 돌아온 장비의 반납을 완료하고 싶다.
37. 관리자로서 장비를 돌려받지 못했다면 사유와 함께 반납 요청을 거절하여 대여 상태를 유지하고 싶다.
38. 관리자로서 전체 직원의 대여·반납·연체 현황과 이력을 확인하여 자산 사용을 관리하고 싶다.
39. 운영자로서 서버 재시작과 재배포 후에도 기록이 남아 데이터를 잃지 않고 싶다.
40. 운영자로서 백업과 복구 절차를 검증하여 장애 시 업무 데이터를 복원하고 싶다.
41. 작업자로서 공개 GitHub 저장소에서 변경 이력을 확인하고 싶다.
42. 작업자로서 변경을 PR로 제출하고 자동 검사 결과를 확인하여 문제가 있는 변경의 병합을 막고 싶다.
43. 운영자로서 관리자에게도 main 보호가 적용되어 직접 push와 강제 push를 막고 싶다.
44. 운영자로서 main 병합 후 프론트·백엔드·DB 변경을 자동 반영하여 수동 배포를 줄이고 싶다.
45. 비개발자 작업자로서 한국어 한 문장 커밋과 자연어 PR 본문으로 사용자에게 달라진 점을 이해하고 싶다.
46. 운영자로서 운영 비밀키와 실제 직원 정보가 공개 저장소에 올라가지 않게 하고 싶다.
47. 운영자로서 배포 실패와 DB 변경 실패를 알아 미완료 배포를 정상 운영으로 오해하지 않고 싶다.

## Implementation Decisions

### 확정한 업무 규칙

- 관리자는 한 명이다. 직원 역할과 관리자 역할을 구분하고 서버에서 권한을 검사한다.
- 운영 서비스는 Google 로그인만 사용한다. 로컬 개발에서만 명시적으로 활성화한 테스트 계정 로그인을 허용하며 운영 노출은 차단한다. 서버는 Google 인증 결과와 사전 등록 이메일 및 계정 활성 상태를 검증한다. 최초 관리자 지정 방식과 실제 이메일은 사용자가 추후 제공하며, 첫 로그인 사용자를 임의로 관리자로 승격하지 않는다.
- 자산은 자산번호로 식별하는 개별 실물 장비다. 자산번호 중복을 허용하지 않는다. 모델별 수량 배정이나 관리자 인도 확정 단계는 두지 않는다.
- 자산 정보는 자산번호, 장비명, 모델, 분류, 설명, 보관 위치, 상태로 구성한다. 사진은 제외한다.
- 대여 신청은 승인 대기·승인·거절·취소를 구분한다. 직원은 본인 대기 신청만 취소할 수 있다.
- 같은 자산에 여러 직원이 신청할 수 있다. 한 건 승인 시 즉시 대여를 시작하고 같은 자산의 나머지 대기 신청을 자동 거절한다.
- 대여는 사용 중·반납 확인 대기·반납 완료를 구분한다. 반납 요청만으로 자산을 다시 대여 가능하게 만들지 않는다. 반납 요청 거절 시 사용 중으로 돌아가며 거절 사유를 남긴다.
- 관리자의 대여 신청·반납 요청 거절에는 사유가 필요하다. 자동 거절은 원인을 구분할 수 있는 사유를 남긴다.
- 반납 예정일은 필수 날짜이며 KST 기준 해당 날짜의 23:59:59까지를 기한으로 한다. 반납 완료 전에는 반납 확인 대기라도 기한 초과 시 연체다. 연체에 따른 자동 반납이나 이용 차단은 없다.
- 수리 중인 자산은 새 신청을 차단하고 기존 대기 신청을 자동 거절한다.
- 자산 삭제는 영구 삭제가 아닌 보관 처리다. 이력은 유지하고 새 신청을 막는다. 사용 중이거나 반납 확인 대기인 대여가 있으면 삭제할 수 없다.
- 직원은 전체 장비와 본인 신청·대여 이력만, 관리자는 전체 현황을 조회한다. 화면에서 메뉴를 숨기는 것만으로 권한을 대신하지 않는다.
- 승인·거절·연체는 웹 화면으로 표시한다. 이메일·메신저 알림은 없다.

### 데이터와 인터페이스

- 인증·직원 허용 목록·자산 관리·대여 신청·대여 및 반납·전체 현황을 모듈로 구분한다. 외부 인터페이스는 HTTP API로 제공하고 프론트는 이를 사용한다.
- 저장 대상은 사용자 식별 정보와 역할·활성 상태, 개별 자산과 보관 여부, 신청과 처리 사유, 대여와 반납 예정일, 반납 요청·처리 결과, 업무 처리 시각과 주체다. Google 로그인 식별자와 이메일은 구분한다.
- 조회, 자산 등록·수정·수리·보관, 본인 신청·취소, 관리자 승인·거절, 본인 반납 요청, 관리자 반납 확인·거절, 직원 접근 관리를 API로 제공한다. 상세 URL과 응답 스키마는 구현 시 계약으로 문서화한다.
- 인증 없음·권한 부족·잘못된 입력·현재 상태와 충돌하는 요청을 구분하고 한국어로 이해할 수 있는 오류를 표시한다. 클라이언트가 보내는 사용자나 역할 정보를 신뢰하지 않는다.
- 승인·자산 상태 변경·반납 완료와 관련 신청 자동 거절은 필요한 변경을 SQLite 트랜잭션으로 묶는다. 한 자산의 진행 중 대여는 최대 한 건이며 반납 확인 대기도 포함한다. 여러 탭·더블 클릭·동시 요청에서도 보장한다.
- UI 캐시의 사용 가능 표시는 참고이며 최종 승인 가능 여부는 서버와 DB에서 재검사한다.

### 배포와 협업

- Go 경량 백엔드와 정적 SPA 프론트를 사용하며 SEO를 요구하지 않는다. SQLite는 Railway 영구 볼륨에 저장한다. 운영 비용을 우선하고 별도 DB 서버나 Redis를 기본 구성에 추가하지 않는다.
- 프론트는 사용자의 기존 유료 Vercel 계정, 백엔드와 데이터는 Railway에 둔다. 영구 볼륨 사용에 따른 단일 인스턴스와 재배포 시 짧은 중단을 수용한다.
- SQLite 마이그레이션은 볼륨 연결 후 HTTP 요청 수신 전에 자동 실행한다. Railway pre-deploy에서 볼륨 DB를 수정하지 않는다. 실패 시 준비 완료로 표시하지 않는다.
- main 병합 후 CI 성공을 확인한 동일 변경으로 프론트와 백엔드를 자동 배포한다. 운영 DB 접근은 운영 환경에 한정하고 PR 검사·미리보기는 운영 DB를 사용하지 않는다.
- DB 변경은 이전 앱과 호환 가능한 추가 방식부터 적용한다. 앱 롤백만으로 DB도 복구된다고 가정하지 않고 백업·복구 방법을 검증한다.
- 공개 저장소 main은 PR 필수, 빌드·테스트 성공 필수, 최신 main 반영 필수이며 관리자도 우회할 수 없도록 한다. 강제 push와 브랜치 삭제를 막는다. 타인 승인 개수는 필수로 하지 않는다.
- Squash 병합과 병합 후 작업 브랜치 삭제를 사용한다. 커밋·PR 제목은 한국어 한 문장, PR 본문은 바뀐 점·확인 결과·배포 전 필요한 일을 자연어로 작성한다. 브랜치는 feature, fix, docs, setup 종류와 짧은 영문 설명을 조합한다.
- OAuth 비밀키, 운영 계정과 DB 파일은 공개 저장소에 넣지 않는다. 운영 값은 배포 환경에 설정하고 테스트에는 가상 정보를 사용한다.

### 조사된 추천안과 미확정 항목

- React·TypeScript·Vite, chi, modernc SQLite 드라이버, goose, OAuth2·OIDC, TanStack Query, React Hook Form·Zod, shadcn/ui·Tailwind가 조사된 추천안이다. Go·SQLite·배포 대상 외 개별 패키지는 아직 최종 채택이나 설치가 완료된 것이 아니다.
- 세션 라이브러리와 SQLite 저장 어댑터는 호환성을 검증한 뒤 정한다. 서버에서 로그아웃·직원 비활성화를 반영할 수 있어야 한다.
- 프론트와 API의 운영 도메인 또는 동일 출처 프록시를 정한 후 쿠키·CSRF·CORS와 OAuth 콜백을 설정한다.
- 아직 결정되지 않은 세부 정책은 구현 전에 기록한다: 최초 관리자 지정, 이미 대여 중인 자산의 수리 전환, 보관 시 대기 신청 처리, 같은 직원의 동일 자산 중복 신청 방지, 기한이 지난 대기 신청의 승인 처리. 이 명세가 이를 사용자 확정 사항으로 간주하지는 않는다.

## Testing Decisions

- 사용자 확인을 받은 주 테스트 경계는 실제 HTTP API와 실제 SQLite를 연결한 통합 테스트다. 내부 함수 호출 순서나 저장소 모킹보다 외부 요청과 응답·다음 조회에서 관찰되는 업무 결과를 검증한다.
- 기존 기본 서버의 httptest 기반 상태 코드·응답 검사를 확장한다. 현재 상태 확인 테스트는 업무 기능 검증을 대신하지 않으며 장비 대여 기능은 아직 구현 전이다.
- 인증·권한, 직원 접근 관리, 자산 변경, 신청 승인·자동 거절, 반납 확인·거절, 연체와 이력 조회를 같은 API 경계에서 검증한다. SQLite 드라이버·외래 키·고유 제약·트랜잭션은 운영과 같은 구성으로 사용한다.
- 같은 자산의 두 신청 동시 승인, 승인과 수리 전환 경합, 승인 더블 클릭, 다른 직원 이력 접근, 비활성 직원의 기존 세션 사용을 테스트한다. 실패한 작업이 일부 상태만 남기지 않는지 확인한다.
- KST 반납 예정일 종료 직전과 다음 날 경계, 브라우저 시간대 차이, 반납 확인 대기 중 연체를 재현 가능한 시간으로 검증한다.
- 서버 재시작과 실제 파일 기반 SQLite 재연결 후 이력 보존을 확인한다. 빈 DB와 기존 DB의 마이그레이션, 실패 시 서버 시작 차단, 백업 복원 후 주요 데이터 조회를 확인한다.
- Google 인증은 테스트용 OIDC 제공자 또는 통제된 경계에서 검증하여 CI가 실제 직원 계정에 의존하지 않게 한다. 운영 콜백과 허용 이메일 로그인은 자격 증명 제공 후 별도로 확인한다. 테스트 인증 경로를 운영에 노출하지 않는다.
- 브라우저 테스트는 직원 신청→관리자 승인→직원 반납 요청→관리자 확인의 핵심 흐름과 권한별 화면 노출을 중심으로 수행한다. 모든 세부 분기를 브라우저와 API에서 중복 검증하지 않는다.
- 입력 오류와 사용자 동작이 중요한 폼은 UI 행동 테스트로 보강한다. 스냅샷이나 라이브러리 자체 기능만을 확인하는 테스트는 피한다.
- PR에서 백엔드와 프론트의 빌드·테스트를 필수 실행하고 필수 검사 이름을 main 보호 정책과 일치시킨다. CI 실패 시 병합을 차단하고 main CI 실패 시 운영 배포를 차단하는지 확인한다.
- main 병합 후 실제 Vercel·Railway 배포, SQLite 마이그레이션, 건강 상태와 로그인 후 핵심 조회를 확인한다. 비밀키나 클라우드 연결이 없으면 자동 배포가 완료됐다고 보고하지 않는다.

## Out of Scope

- 비밀번호 로그인, 공개 회원가입, 운영 서비스의 Google 외 로그인 제공자. 명시적으로 활성화하는 로컬 개발 테스트 계정은 예외다.
- 여러 관리자 체계, 다단계 승인, 별도 인도 확정 절차.
- 모델별 수량만 관리하는 재고 모델과 관리자 장비 배정 단계.
- 장비 사진·파일 업로드, 이메일·메신저 알림.
- 미래 날짜 예약, 대여 연장, 연체 자동 반납·자동 이용 차단.
- 대여 이력이나 자산의 영구 삭제.
- SEO와 서버 렌더링 요구, 별도 검색 서버·메시지 큐·실시간 소켓.
- 무중단 배포, 다중 인스턴스·다중 리전, 높은 동시 쓰기 부하 최적화.
- 타인 PR 승인 필수 조건, 영문 기술 접두어가 필수인 커밋 규칙.
